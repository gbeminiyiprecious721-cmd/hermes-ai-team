### A known-limitation waiver mechanism (built, proven, reusable for future projects)
`GATE_WAIVERS.json` in a project folder = `{"waivers": [{"gate": "Testing", "accepted_finding_ids": ["QA-003"], "reason": "...", "decided_by": "...", "decided_at": "..."}]}` (or `"accept_all_remaining": true` instead of a finding-id list). It is deliberately narrow and audited, not a way to fake success:
- Only applies to a gate that is CURRENTLY failing; a passing gate is untouched.
- Requires both `reason` and `decided_by` - a waiver with either missing is silently ignored (still fails closed).
- Covers only the EXACT finding ids it names (or an explicit accept-all); if QA reports even one finding not named in the waiver, the gate still fails - a waiver cannot be used to blanket-approve future, unseen problems.
- Never edits or hides the original QA output: the result keeps `original_status`/`original_reason`; the pass is marked `waived: true` with who decided it and when, and recorded in `state['gate_waivers_applied']` plus an activity event (`GATE_WAIVED`), so it is visible in Mission Control and in `state.json`, not silent.
- Verified with 6 unit cases before it ever touched a real project: no file (fails), full coverage (passes, keeps the original reason), missing reason (ignored), partial coverage of current findings (still fails), `accept_all_remaining` (passes), wrong gate name (ignored).
- Example file: `code/tools/example_GATE_WAIVERS.json`. Implementation: `code/tools/patch_pf_waiver.py`.

### A real reliability bug found and fixed: a timeout was cached as a hard failure
The Release/DevOps step failed twice with `Model invocation timed out after 120 seconds.` on BOTH the primary and fallback free model. An immediate retry (`--resume`) failed again in 16 seconds - far too fast to be a real second attempt. Cause: `_provider_failure_kind()` only recognised words like "overloaded"/"service unavailable"/HTTP 502-504 as retryable; a plain timeout fell through to a hard `FAILED`, which the pipeline then cached as `UNAVAILABLE` for `overload_cooldown_seconds` (default 300 s) - so the retry never even attempted the model again, it just replayed the cached failure. Fixed: `_provider_failure_kind()` now also treats "timed out", "timeout", "connection reset" and "connection aborted" as `RETRYABLE_OVERLOAD`, which the pipeline already never caches (by design, so the very next call retries for real). Verified with the exact failing message before and after the fix. This affects every specialist and every free-model call, not only Release/DevOps - a general reliability improvement. Implementation: `code/tools/patch_pf_timeout_retryable.py`.

## Q6. Possible Tailscale Serve exposure - needs the owner to verify from an outside device

Cause not established - could be something specific to how the assistant's sandboxed browser tool routes traffic (plausible, unverified), or a genuine Tailscale Serve/ACL misconfiguration (would be serious if true). **Action needed**: check from a device confirmed *not* on the tailnet - e.g. a phone on cellular data with the Tailscale app disconnected - whether the login page loads.
